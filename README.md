# ai-agents

Команда ИИ-агентов, которая ведёт Instagram фитнес-тренера; тренер общается с агентами в Telegram.

## Локальный запуск

Нужны Docker и Docker Compose v2.
Установка с нуля (macOS, Linux-VPS), справочник переменных `.env` и где взять ключи — в [docs/SETUP.md](docs/SETUP.md);
сквозная проверка всего окружения с реальными ключами — `make m0-check` (отчёт в `m0-results/report.md`).
Ручная проверка всех кирпичей с реальными ключами по шагам — [docs/M0-MANUAL.md](docs/M0-MANUAL.md).

```bash
cp .env.dist .env   # безопасные dev-значения по умолчанию
make up             # собрать и поднять стек, дождаться healthcheck
curl 127.0.0.1:8080/readyz
make logs           # логи
make down           # остановить (данные в volume сохраняются; `docker compose down -v` — удалить)
```

Сервисы: `app`, `migrate` (одноразовый: применяет миграции до старта `app`), `postgres` (pgvector), `redis` (с паролем),
`s3` ([RustFS](https://rustfs.com) — S3-совместимое хранилище), `media-worker` (Монтажёр: монтирует видео ffmpeg-ом на
образе `media` в своём контейнере, без токенов ботов, ключа Claude и базы, без портов; см. «Монтажёр» ниже). Клиент в
приложении — minio-go, работает с любым S3.
Бакет для медиа (`S3_BUCKET`) приложение создаёт само при старте.

Наружу опубликованы только `app` (`127.0.0.1:${APP_HOST_PORT}`) и `postgres` (`127.0.0.1:${POSTGRES_HOST_PORT}`, для отладки).
Redis, S3 и Bot API доступны только внутри сети compose, поэтому по умолчанию приложение запускается в compose
(запуск на хосте — ниже).
Консоль RustFS, если нужна: `docker compose exec s3 ...` или временный `docker-compose.override.yml` с портом на `127.0.0.1`.

- `/healthz` — liveness: процесс жив.
- `/readyz` — readiness: статусы (`ok`/`fail`) PostgreSQL, Redis и S3; `503`, если хоть одна зависимость недоступна.
  Текст ошибок — только в логе.

### Миграции

Файлы — `migrations/NNN_описание.up.sql` + `NNN_описание.down.sql` (golang-migrate). В compose их применяет сервис `migrate`.

```bash
make migrate        # применить все новые
make migrate-down   # откатить одну
```

Приложение миграции не применяет — только `cmd/migrate` (сервис `migrate`). Он работает без таймаута старта:
по SIGINT/SIGTERM дожидается конца текущей миграции и выходит с ошибкой, так что база не остаётся `dirty`.

### Запуск на хосте (`make run`)

Удобно для отладки. Зависимости остаются в compose, а Redis и S3 нужно временно опубликовать на `127.0.0.1`:

```bash
cat > docker-compose.override.yml <<'YAML'   # в .gitignore; compose подхватывает его сам
services:
  redis:
    ports: ["127.0.0.1:6379:6379"]
  s3:
    ports: ["127.0.0.1:9000:9000"]
YAML

cat > .env.local <<'ENV'                      # в .gitignore; make run читает его после .env
POSTGRES_HOST=localhost
REDIS_ADDRESS=localhost:6379
S3_ENDPOINT=localhost:9000
HTTP_ADDRESS=127.0.0.1:8082
ENV

docker compose up -d --wait postgres redis s3
make migrate                                  # миграции применяются в compose
make run
```

`POSTGRES_PORT` в `.env.local` нужен, только если `POSTGRES_HOST_PORT` не 5432. `HTTP_ADDRESS` — порт, не занятый `app` из compose (8080)
и Bot API (8081), чтобы всё могло работать одновременно. Bot API на хосте недоступен: для него опубликуй порт 8081 так же
и задай `TELEGRAM_BOT_API_URL=http://localhost:8081`, либо используй публичный API.
Когда override не нужен, удали его: иначе `make up` тоже опубликует Redis и S3.

### Профиль `telegram`

Локальный сервер Telegram Bot API нужен, чтобы боты могли скачивать файлы до 2 ГБ (публичный API отдаёт ботам только до 20 МБ).
Он требует `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` — их выдают на https://my.telegram.org (API development tools).
Заполни их в `.env` и подними:

```bash
docker compose --profile telegram up -d
```

Приложение обращается к нему по `TELEGRAM_BOT_API_URL`; том с файлами Bot API смонтирован в `app` только на чтение по тому же пути
(`/var/lib/telegram-bot-api`), так что локальный путь из `getFile` можно читать напрямую. `app` добавлен в группу
сервера Bot API (`group_add: ["101"]`): сервер создаёт медиа с правами 0640.

### Telegram-шлюз

`internal/gateway` ведёт четырёх ботов (Маркетолог, Копирайтер, Монтажёр, Дизайнер) в одном сервисе: long polling
через локальный Bot API, только супергруппа команды и пользователи из белого списка, роутинг по `@упоминаниям`,
реплаям и топикам, команды `/plan`, `/idea`, `/ideas`, `/idea_done`, `/idea_drop`, `/status`, `/pause`, приём текста и видео (до 2 ГБ; сохраняется в S3).
Без `TELEGRAM_*_TOKEN` шлюз выключен. Отправка от имени роли — `gateway.Sender` (файлы только из
`TELEGRAM_OUTBOX_DIR`); входящие события получает `gateway.Handler` (в приложении — `teamchat.Handler`, см.
«Задачи и согласование»). Handler должен
быть быстрым и идемпотентным: записать задачу по ключу `chat_id`+`message_id` и вернуться, тяжёлая работа — в очереди.
Файл читается через `Media.Open` и сразу копируется к себе (S3): Bot API может удалить старые файлы. Обработчик,
который файлы пока не обрабатывает, реализует `gateway.MediaFilter`, и шлюз их не скачивает. Пересланный
текст (`Event.Forwarded`) агенты считают данными, а не инструкцией. Настройка ботов и группы, переменные и ручная проверка —
[docs/SETUP.md](docs/SETUP.md), раздел 6, «Telegram-боты».

## Транскрипция видео

`transcribe` извлекает речь из видео (ffmpeg) и отдаёт JSON с текстом, сегментами и таймкодами слов (Whisper `whisper-1`).
Нужны `ffmpeg`/`ffprobe` и `OPENAI_API_KEY` в `.env`:

```bash
make transcribe ARGS="-in video.mp4 -out result.json"   # -lang ru по умолчанию (WHISPER_LANGUAGE)
```

В образе с ffmpeg: текущая папка монтируется в `/work` (рабочая папка образа). Пути `-in` и `-out` — относительно неё,
`--user` нужен, чтобы `result.json` на хосте принадлежал вам и был доступен для записи:

```bash
make media-image
docker run --rm --env-file .env --user "$(id -u):$(id -g)" -v "$PWD:/work" ai-agents-media:local \
  -in video.mp4 -out result.json
```

Если в роликах фоновая музыка и паузы не находятся, подними `TRANSCRIPTION_SILENCE_NOISE_DB` (например, до `-25`).

### Известные ограничения

- **`whisper-1` отключат 26.02.2027.** OpenAI объявила его deprecated, а это единственная её модель с пословными
  таймкодами. Замену (например, ElevenLabs Scribe) нужно выбрать до этой даты.
- Фильтр галлюцинаций Whisper эвристический: сегмент отбрасывается, если Whisper уверен, что там нет речи, и текст
  распознан плохо (`avg_logprob < -1`), или это повтор (`compression_ratio > 2.4`), распознанный плохо или поверх тишины.
  Отброшенные фрагменты пишутся в лог (`transcription: dropped hallucinated segment`).
- На стыке кусков длинного видео (длиннее 10 минут) у обрезанного сегмента теряется пунктуация, а слово, повторённое
  совсем без паузы, может склеиться с предыдущим.

## Черновая склейка (`roughcut`)

`roughcut` делает из сырого вертикального видео черновой рилс по транскрипту T3.1: сжимает паузы длиннее 0,3 с до короткого вдоха,
слова-паразиты («э», «эм», «ммм») и неудачные дубли, склеивает остальное ffmpeg с перекодированием в H.264 + AAC
(разрешение и 9:16 исходника сохраняются). Сеть не нужна, если транскрипт уже есть:

```bash
make transcribe ARGS="-in video.mp4 -out transcript.json"          # один раз, платно
make roughcut ARGS="-in video.mp4 -transcript transcript.json -out cut"
make roughcut ARGS="-in video.mp4 -transcript transcript.json -out cut -plan-only"   # только план, без рендера
make roughcut ARGS="-in video.mp4 -out cut"                         # без -transcript: сначала транскрипция (OPENAI_API_KEY)
```

В образе `media` (`make media-image`) — так же, как `transcribe`, но с `--entrypoint /app/roughcut`:

```bash
docker run --rm --env-file .env --user "$(id -u):$(id -g)" -v "$PWD:/work" --entrypoint /app/roughcut \
  ai-agents-media:local -in video.mp4 -transcript transcript.json -out cut
```

Флаги: `-max-pause 300ms`, `-similarity 0.7`, `-fillers "э,эм,м,хм"` переопределяют `ROUGHCUT_*` из `.env`;
`-lang` — язык транскрипции, если её запускает сама команда.

Что лежит в папке `-out` (файлы с правами по umask, обычно 0644: их читает app под другим пользователем):

| Файл | Что это |
|---|---|
| `roughcut.mp4` | склейка; нет в режиме `-plan-only` и после ошибки рендера (видео прошлого запуска удаляется заранее) |
| `plan.json` | план монтажа (EDL): `keep` — сохраняемые интервалы исходника в секундах, `cuts` — вырезанные куски с причиной (`pause`, `filler`, `retake`) и словами, `takes` — решения по дублям, `candidates` — спорные повторы, оставленные в ролике, `frame_rate` — частота кадров результата, `settings` — пороги, `mode` и `edit` — режим и правки Монтажёра (`edit.cut_time` — вырезанное по времени, `edit.titles` — подписи упражнений по времени исходника, `edit.mute` — без звука) |
| `decisions.log` | лог решений на русском: итоги, каждый вырезанный дубль с причиной, спорные повторы, паразиты и паузы |
| `transcript.json` | транскрипт в формате T3.1, пересчитанный на время склейки, с пунктуацией сегментов (для субтитров T3.3) |
| `source-transcript.json` | транскрипт исходника, если его делала сама команда: в следующий раз передай его в `-transcript` |

Как читать лог: строка `Дубль 1 (0:12.0–0:18.3) оборван на «давайте при…», оставлен дубль 2 (0:19.0–0:26.4) «…»`
значит, что фраза с 12-й секунды исходника вырезана, потому что тренер оборвал её и начал заново, а в ролик вошёл
последний вариант. «Начат заново (повторено 100% слов)» — начало фразы повисло («Сегодня мы…») и сказано снова
с продолжением. В разделе «Спорные повторы» — законченные фразы, сказанные ещё раз: ритм («Вдох, выдох. Вдох,
выдох»), перечисление («делаем по десять приседаний… выпадов…») или повтор целой фразы. Они не вырезаются автоматически: решает
Монтажёр (модель, T3.4c) или человек. У каждого в `plan.json` есть `id`, индексы слов (`earlier_words`, `later_words`) и готовый
интервал вырезания `cut` (с полями вокруг слов и по сетке кадров): чтобы вырезать, достаточно перечислить `id` —
`make roughcut ARGS="-in video.mp4 -transcript transcript.json -accept 0,2"`, план пересоберётся с теми же
правилами (`id` стабильны при тех же транскрипте и порогах). Время в логе — по исходнику, в формате
минуты:секунды.доли.

Правка плана вручную или агентом: отредактируй `keep` в `plan.json` (интервалы по возрастанию, без пересечений,
не больше 500, каждый не короче кадра) и отрендери его с тем же транскриптом:
`make roughcut ARGS="-in video.mp4 -transcript transcript.json -plan cut/plan.json -out cut2"` (`-plan` без
`-transcript` — ошибка, а не повторная платная транскрипция). Транскрипт и видео пересчитаются по новым интервалам;
`cuts`, `takes`, `candidates` и `frame_rate` из файла только поясняют, частота кадров берётся из исходника.

Как это решается:

- **Паузы и точки разреза (T3.19b).** Тайминги слов Whisper неточны на десятки миллисекунд, а окончания русских
  слов в них часто «съедены», поэтому разрез ставится по уровню звука исходника (RMS в окнах 10 мс, звук декодируется
  отдельно за ~1 с на 4 минуты; при рендере по готовому плану `-plan` и в тренировке уровни не читаются): речь ищется
  до 0,3 с за краями слов (с «дыркой» смычки согласной до 0,12 с), порог речи — 40 % пути от шумового пола
  (10-й процентиль окон) к громкой речи (95-й), не ниже пола + 10 дБ, поэтому вдохи и шум между фразами речью не
  считаются, а затухание в цифровую тишину — считается. Пауза, которая на слух длиннее `ROUGHCUT_MAX_PAUSE`
  (по умолчанию 0,3 с), сжимается до вдоха 0,15 с (± полкадра сетки — 0,13–0,17 с при 30 к/с): хвост фразы кончается в
  самой тихой точке 0,06–0,10 с после её звука (из равных — в самой поздней), следующая фраза начинается так, чтобы
  тишины осталось на вдох, но не ближе 0,04 с к её звуку; точки — на сетке кадров. Вокруг вырезанных слов (паразит,
  дубль, правка) хвост такой же, начало следующего слова — в самой тихой точке между полем 0,12 с и 0,04 с до его
  звука; если тишины меньше вдоха, следующее слово начинается раньше (не раньше конца вырезанного), потом хвост
  длиннее (не дальше начала вырезанного). Перед первым звуком остаётся 0,1 с, после последнего — 0,15 с. Если звук не
  отличает речь от тишины (музыка, ровный шум, контраст меньше 15 дБ) или не прочитан, работают поля вокруг слов
  0,12/0,18 с (если порог меньше суммы полей, поля уменьшаются пропорционально). На каждом стыке звук гасится и
  поднимается за 10 мс — без щелчков и без изменения длины. В `decisions.log` — уровни звука (шум p10, громкая речь
  p95, порог речи, дБFS — по ним калибруется порог), как поставлены точки разреза и сколько пауз длиннее 0,3 с осталось
  в ролике (`plan.json`: `sound_levels`, `sound_cuts`, `long_pauses`). Whisper ещё и растягивает слова в тишину
  (конец позже на 0,35 с, начало раньше на 0,3 с, границы сходятся посреди реальной паузы): если на границе Whisper
  звука нет, речь ищется и внутри слова (не дальше его середины и 0,4 с), поэтому такая пауза тоже сжимается до вдоха;
  окончания не обрезаются — внутрь поиск идёт, только когда граница тихая. Шумовой пол считается по окнам громче
  −100 дБFS (цифровая тишина гейта не опускает порог под шум комнаты в других паузах), а если среди них только речь —
  пол не ниже −90 дБFS. Тишина до первого и после последнего слова
  вырезается. Если в `.env` осталось `ROUGHCUT_MAX_PAUSE=400ms` из старого `.env.dist`, новое значение по умолчанию не
  применится — поправьте строку на `300ms` (или удалите её).
- **Паразиты** — только целые слова из `ROUGHCUT_FILLERS`, повторы букв не важны («эээ» = «э»). «Ну», «а», «вот» не
  трогаются, пока их нет в списке; «м» после числа («400 м») — единица, не мычание.
- **Дубли** режутся, только когда попытка явно неудачная, и всегда остаётся последняя:
  - оборванное слово: после паузы (≥ 0,2 с или граница фразы) слова повторяются, а последнее слово попытки —
    начало слова в новом дубле («давайте при… давайте приступим»). Обрывок короче полного слова минимум на 2 буквы
    и не длиннее 70% его, а слово перед `.`, `!`, `?` в тексте сегмента обрывом не считается — так «зал / зале»,
    «ног / ноги», «присед. Приседаем», «мост. Мостик» остаются;
  - повисшее начало: после паузы (≥ 0,3 с, паразита или с нового сегмента Whisper) фраза начинается так же, как
    попытка, и идёт дальше, а попытка оборвалась без знака или на «…»/«—» («Сегодня мы… Сегодня мы разберём»).
  Законченный повтор (после запятой или точки, той же длины, цепочка одинаковых фраз) не режется, а попадает в
  `candidates`. Счёт («раз, два, три…») дублем не считается. Ищется в пределах 20 с и 30 слов, сходство —
  `ROUGHCUT_RETAKE_SIMILARITY` слов попытки, сказанных снова по порядку.
- **Склейка** точная по времени и декодирует только то, что остаётся (T3.19b): соседние куски (промежуток меньше
  3 с) группируются, каждая группа — отдельный вход исходника с перемоткой (`-ss` перед `-i` — демуксер прыгает к
  ключевому кадру, на 0,5 с раньше первого куска группы, `-t` — до 0,5 с после последнего); внутри группы поток
  декодируется один раз (`split`/`asplit`). Группа в первых 2 с исходника читается с начала, одна группа — весь
  исходник, как раньше. Входов не больше, чем помещается в бюджет памяти декодеров ~1,3 ГиБ:
  бюджет / (ширина × высота × байт на отсчёт × 1,5 × 16 кадров), в пределах 2…8 — 7 для 4K 8 бит, 4 для 4K 10 бит
  (HDR iPhone), 8 для 1080p (у каждого входа свой декодер с двумя потоками до конца рендера; ревью намерило 1,4 ГБ RSS
  на 8 входов 4K H.264 и 2,2 ГБ на 8 входов 4K HEVC 10 бит); лишние группы сливаются там, где промежутки короче. Правка минутного рилса из 4-минутного 4K-исходника
  декодирует около минуты, а не четыре. Для 4K HDR (HEVC 10 бит) при разреженном отборе выигрыш скорости мал (рилс
  22 с из 11 далёких кусков — 94 с, 4,3 с на секунду рилса): каждый кусок декодируется от своего ключевого кадра, а
  тонмаппинг стоит столько же; рендер таких кусков партиями или из 1080p-копии — отдельная задача. Видео приводится к постоянной частоте кадров — номинальной частоте исходника без округления
  (`r_frame_rate`, например 30000/1001; средняя, если номинальная неизвестна или выше 60), но не выше 30 к/с:
  слоумо и 60 к/с → 30, 59.94 → 29.97, 50 → 25 (берётся каждый второй кадр — кадр времени звука, монтажная
  точность — кадр результата) —
  и режется по номерам кадров, звук — по сэмплам. Края интервалов выровнены по сетке кадров, а время считается
  от первого сэмпла звука (учитываются `start_time` аудио и файла), так что картинка, звук и субтитры не
  разъезжаются на телефонных роликах с переменной частотой и на файлах с ненулевым начальным временем. На каждом стыке аудиофейд 10 мс. Граф фильтров передаётся ffmpeg файлом
  (`-/filter_complex` в ffmpeg 7+, `-filter_complex_script` в 6.x). Поворот из метаданных телефона применяется:
  ролик, записанный как 1920×1080 с поворотом, выходит 1080×1920. Временные файлы удаляются, `roughcut.mp4`
  появляется только целиком.
- **Звук и динамика черновика Монтажёра** (T3.15, `media-worker`; CLI `roughcut` их не включает): склеенный звук
  проходит лёгкий шумодав речи (`highpass` 80 Гц + `afftdn`, только разговорный ролик; порог шума — на 36 dB ниже
  громкости записи, задержка `afftdn` 25 мс компенсируется) и выравнивается до −14 LUFS. Громкость исходника
  меряется `ebur128` при извлечении звука для Whisper и хранится в транскрипте, поэтому рендер и правки не
  анализируют звук заново: одно усиление (`volume`) и лимитер пиков (`alimiter`, −2 dBTP — после AAC не выше
  −1,5 dBTP), динамика речи не сжимается. Лимитер срезает пики и уводит громкость ниже цели, поэтому перед рендером
  звук склейки отдельно (без картинки, секунды) прогоняется той же цепочкой и меряется, усиление поправляется на
  промах (до 3 проходов, пока промах больше 0,1 LU; после первого шаг делится на наклон «громкость на dB усиления»,
  поправка не больше ±12 dB) — итог −14 ± 0,5 LUFS. Лимитер работает на звуке с передискретизацией до 192 кГц и держит
  пики между отсчётами: после AAC true peak не выше −1,0 dBTP. Готовый файл меряется ещё одним проходом по звуку, и в
  `decisions.log` пишется этот замер (громкость и true peak после AAC), а не цель. Звук кодируется в AAC 192k (на
  128k кодек поднимал пики сибилянтов на несколько dB); если true peak файла всё же выше −1,0 dBTP, звук
  пересобирается из исходника с потолком лимитера ниже на превышение + 0,5 dB (не больше 3 dB) и заново подобранным
  усилением (проходы только по звуку; видео копируется, секунды) — громкость остаётся у цели, а не падает всем звуком под −14,5 LUFS; если это не удалось,
  файл остаётся как есть с пометкой в `decisions.log`. Если предварительный замер упал,
  рендер идёт с усилением по замеру исходника, без поправки (ошибка — в лог воркера и пометка в `decisions.log`). Без измерения (старый транскрипт) — `loudnorm` в один проход. В разговорном
  ролике на склейках кадр чередуется — обычный и приближенный на 9 % (jump-cut zoom, статично; кусок короче 1,2 с
  кадр не меняет): приближается уже кадр 1080×1920 перед субтитрами. Строки об этом — в конце `decisions.log`
  («Звук и кадр»: громкость исходника, цель, усиление с поправкой и итоговый замер, порог шумодава, число зумов). Настройки —
  `MEDIA_WORKER_LOUDNESS`, `MEDIA_WORKER_DENOISE`, `MEDIA_WORKER_ZOOM` (docs/SETUP.md).
- **Ролик без звука** не поддерживается: резать не по чему. Команда завершается ошибкой `source has no audio stream`
  до записи файлов.

### Ограничения склейки

- Решения только по транскрипту: если Whisper растянул слово на тишину или не услышал оговорку, пауза или дубль
  останутся. Тишина внутри «слова» не режется.
- Рестарты без пунктуации в тексте Whisper («Сегодня мы, сегодня мы разберём») не режутся, а идут в `candidates`.
  Дубль, начатый с другого слова («Итак, сегодня мы…» после «Сегодня мы…»), не находится. Брошенная фраза без
  повтора («так, нет, стоп») не вырезается. Порог сходства подбираем на роликах тренера.
- Пунктуация сегмента сохраняется, если слова транскрипта совпали со словами текста сегмента: знак конца
  предложения у вырезанного слова переходит на предыдущее, а если вырезано начало предложения, первая оставшаяся
  буква становится заглавной. Иначе (например, «10» в тексте и «десять» в словах) текст собирается из слов без
  пунктуации.
- Временные файлы (граф фильтров, рендер) пишутся в `TMPDIR` (по умолчанию `/tmp`) и в скрытую папку внутри
  `-out`. Если контейнер запущен с `--read-only`, смонтируй tmpfs: `--tmpfs /tmp` (и `-out` должен быть
  доступен для записи).
- Не больше 500 кусков на ролик. Рендер 3–5-минутного ролика 1080×1920 на VPS занимает минуты; он ограничен
  `FFMPEG_TIMEOUT` (10m).

## Субтитры

`subtitles` делает субтитры в стиле Reels по транскрипту из `transcribe` или по `transcript.json` черновой склейки
(`roughcut`: тот же формат на новой шкале, с пунктуацией сегментов; стыковку проверяет `TestRoughCutTranscriptToSubtitles`):
короткие титры, акценты на ключевых словах, кадр 1080×1920. Рендер — ASS через libass (фильтр `ass` в ffmpeg),
шрифты — из `SUBTITLES_FONTS_DIR` (`assets/fonts`: Manrope Medium и Fira Sans Extra Condensed ExtraBold, обе под
SIL OFL; лицензии и источники с sha256 — рядом, в `SOURCES.txt`).

```bash
make subtitles ARGS="-in video.mp4 -transcript result.json -out reel.mp4"          # видео с субтитрами
make subtitles ARGS="-transcript result.json -out subtitles.ass -ass-only"          # только .ass, без рендера
make subtitles ARGS="-in video.mp4 -transcript result.json -out reel.mp4 -accents 'присед,3 подхода' -karaoke"
```

В образе `media` (ffmpeg с libass и шрифты уже внутри):

```bash
docker run --rm --env-file .env --user "$(id -u):$(id -g)" -v "$PWD:/work" --entrypoint /app/subtitles \
  ai-agents-media:local -in video.mp4 -transcript result.json -out reel.mp4
```

Флаги: `-style file.yaml` — стиль (иначе `SUBTITLES_STYLE_FILE` или встроенный); `-accents` — акценты через запятую
вместо автоматических; `-karaoke` — подсветка произносимого слова (своим цветом, не цветом акцента);
`-fit pad|crop` — как привести видео другого размера к 1080×1920 (`pad`, по умолчанию: кадр целиком, поля чёрные;
`crop`: заполнить кадр, обрезав края). Выход — MP4, H.264 (High, yuv420p, `veryfast`, CRF 20) + AAC 192k 48 kHz (T3.19b: на 128k кодек поднимал true peak ярких звуков на несколько dB),
`+faststart`; HDR (HLG/PQ) сначала уменьшается до 1080×1920, потом тонмаппится в SDR bt709;
видео пишется во временный файл рядом с `-out` и переименовывается только после успешного рендера, так что битого
файла на месте `-out` не остаётся. Коды выхода: 0 — готово, 1 — ошибка, 2 — видео записано, но libass не нашёл
фирменный шрифт и подставил другой (шрифт назван в сообщении). Пустой транскрипт — предупреждение, видео без титров.

**Стиль по умолчанию — как у референсов** (T3.17, выбор владельца по пяти рилс-образцам): речь по **одному слову**
(число с единицей — одним событием: «10 повторений», «3 подхода» | «10 повторений», «10 000 шагов»), строчными, без
знаков конца предложения и кавычек, тире не показывается, мелко — Manrope Medium 48 px, чёрный `#111111` на белой
непрозрачной плашке (ASS BorderStyle 3: плашка рисуется вокруг слова с отступом 9 px и всегда ему по размеру) у левого поля Instagram (x 140) на ~31 % высоты (y 600), сразу под зоной хука. Слово
держится до следующего (без мигания), слово короче 0,15 с показывается вместе со следующим, перед паузой — не дольше
1,5 с. Без акцентов и виньетки: контраст даёт плашка, хуку и пунктам — тень 3 px (75 % чёрного). Сверху по центру — заголовок-хук и после него пункты и цифры на
экране (стиль `hook`), у правого края на уровне слов — белый ник тренера с тенью и значком Instagram
(`REELS_HANDLE`), в последние 2 с — карточка с ником (раздел «Монтажёр»). Раздел `layout.mode` (`word`/`phrase`),
`word_box`, `handle`, `end_card` в `assets/subtitles/style.yaml`; валидация держит плашку, хук с пунктами (4 строки),
подписи упражнений и ник врозь и вне зон интерфейса.

**Фразовый стиль** (прежний, до T3.17) — `assets/subtitles/style-phrase.yaml` (в образе `media` —
`/app/subtitles-style-phrase.yaml`), включается `SUBTITLES_STYLE_FILE`: мелкий текст цвета слоновой кости (`#F5F0E1`) шрифтом Manrope Medium
56 px — на телефоне это около 20 pt (кадр 1080 px ≈ 390 pt), крупнее основного текста iOS (17 pt) и на треть мельче
типичных субтитров Reels; акценты — тёплый жёлтый `#F2B94B`, Fira Sans Extra Condensed ExtraBold капсом, 64 px
(узкие капители при том же кегле выглядят мельче). Без обводки и подложки: читаемость даёт тёмная виньетка от верхнего
края, которую ffmpeg прожигает под титрами: ровное затемнение 60 % от края до низа самого высокого титра (отступ +
три строки, 500 px), затем плавное гашение на 320 px. На белом фоне это даёт контраст около 5:1 для текста и 3:1 для
акцента (проверено рендером). Плюс лёгкая тень 2 px, чёрная 40 %: на затемнении она лишь смягчает край букв, а там,
где виньетки нет (позиция `middle` или виньетка выключена), отделяет текст от светлого фона. Титры сверху. Строка — до 22 символов, до двух
строк; в фразе длиннее строки акцент стоит отдельной строкой (тогда строк три).

**Стиль под брендбук.** Встроенный стиль целиком, с комментариями, — `assets/subtitles/style.yaml`. Скопируйте его,
поменяйте шрифты, цвета, размеры, виньетку, положение (`top`/`middle`/`bottom`) и словарь тренера (`accent.words`),
передайте `-style` или `SUBTITLES_STYLE_FILE`. Поля, которых нет в файле, берутся из встроенного стиля; неизвестное
поле, управляющий символ, полупрозрачный (AA < 80) текст, строка длиннее, чем помещается между отступами, или блок
титров, который не помещается между отступом и зоной интерфейса, — ошибка. Новый шрифт кладите в `assets/fonts` вместе
с лицензией: статический TTF/OTF (вариативные шрифты libass 0.17 из папки не выбирает); имя в стиле — устаревшее имя
семейства с начертанием, как его ищет libass («Manrope Medium»), последнее в `fc-scan --format '%{family}\n' font.ttf`.

**Безопасные зоны** (кадр 1080×1920, константы `SafeZone*` в `internal/subtitles/style.go`): сверху 250 px — панель
Reels, снизу 420 px — подпись, звук и автор, справа 140 px — кнопки. Отступы стиля не могут быть меньше
(`margin_top` ≥ 250, `margin_bottom` ≥ 420, `margin_side` ≥ 140 — одинаковый слева и справа, чтобы текст стоял
по центру). По умолчанию текст сверху, с 260 px; три строки — до ~500 px.

Как режется текст: титр — до двух строк по 22 символа. Новый титр — после конца предложения или сегмента Whisper,
после паузы от 0,3 с, после запятой или тире, если набрано полстроки и остаток фразы не короткий хвост (дольше 0,8 с
и длиннее строки), и когда не влезает в строки или в 3,5 с; хвост короче 0,8 с доклеивается к предыдущему титру, если
помещается. Предлоги, союзы и «не» не отрываются от следующего слова, число — от единицы («10 повторений», составное
«двадцать пять повторений»), частицы «же/ли/бы» — от предыдущего; счёт («раз два три», «1 2 3») не склеивается,
а связка длиннее строки разбивается обратно на слова. Слово длиннее строки сжимается по ширине (`\fscx`), чтобы не
выйти за поля. Пунктуацию Whisper не ставит у слов: слова раскладываются по сегментам по времени, и внутри сегмента
выравниваются с его текстом (наибольшая общая подпоследовательность), так что расхождение в одном сегменте не сдвигает
остальные. Тайминг: титр появляется за 50 мс до первого слова, держится 100 мс после последнего, не короче 0,8 с
(если есть место), не наезжает на следующий; разрыв короче 0,3 с закрывается, чтобы текст не мигал.

Акценты: число с единицей (не счёт) и слово из словаря тренера — всегда (не больше `accent.max_per_cue` на титр);
иначе самое длинное значимое слово от 7 букв (не служебное и не привычная команда вроде «держим», «тянем») — но не в
титре сразу после титра с акцентом. Так акцент получает примерно каждый третий титр. Словарь: запись от 4 букв
совпадает и с формами на 1–3 буквы длиннее, короче — только точно («вес» не «весь»). Явный список (`-accents`, позже —
от Монтажёра) заменяет автоматику. Обратный слэш из речи удаляется, фигурные скобки выводятся как текст.

## Агенты и LLM

- **Агент** — папка `agents/<name>/` с файлом `agent.md`: YAML frontmatter (`name` = имя папки, `display_name`,
  `model`, `tools`, `skills`, `skill_overrides`) и тело — системный промпт роли.
- **Общие скиллы** — `skills/<skill>/SKILL.md` (`SKILLS_DIR`): frontmatter `name`, `description` и тело — инструкция.
  Агент подключает скилл по имени в `skills:`, один скилл может использоваться несколькими агентами.
- **Доработка скилла под агента** — `skill_overrides: {<skill>: "<инструкция>"}` в `agent.md`. Когда агент
  вызывает `load_skill`, текст дописывается к общему SKILL.md. Override на скилл не из `skills:` — ошибка старта.
- **Локальные скиллы** (необязательно) — `agents/<name>/skills/<skill>/SKILL.md`. Локальный скилл с именем
  общего — ошибка старта.
- Runtime добавляет к роли каждого агента общие правила проекта (`agents.SafetyRules`) и список его скиллов.

Агенты и скиллы проверяются при старте: ошибка — приложение не стартует, текст с путями к файлам в логе.
Папки с префиксом `_` — шаблоны, они не загружаются. Шаблон — `agents/_example/`: скопируй его в
`agents/<name>/` и поменяй `name`. Новый инструмент регистрируется модулем в fx-группе `agents.ToolsGroup`.

Агенты команды — `agents/marketer`, `agents/copywriter` и `agents/editor`: имя агента совпадает с ролью бота в Telegram-шлюзе,
задача сообщения уходит агенту целевой роли. Пока это минимальные заготовки для ручной проверки M1: Маркетолог
(план по `/plan`, карточка идеи по `/idea` — инструментом `submit_idea`) и Копирайтер (сценарий рилс: хук, раскадровка, текст в кадре, подпись; вопросов
вместо черновика не задаёт, недостающее помечает `[уточнить у тренера: …]`) ищут в базе знаний; голос бренда
(T2.1) и полноценные скиллы появятся позже. Монтажёр монтирует детерминированным конвейером в `media-worker`, а
модель (`agents/editor`, правила монтажа в его промпте) только решает, что вырезать: по подписи, правке и спорным повторам —
строгим планом через инструмент `submit_edit` (`internal/editplan`), который app проверяет до монтажа;
Дизайнера пока нет: за него отвечает `internal/teamchat` фиксированным текстом.

Ручная проверка с настоящим ключом (`ANTHROPIC_API_KEY` в `.env`): ответ агента и расход токенов и денег —
`make agent-run AGENT=copywriter PROMPT="Сценарий рилс про планку"`. Шаблон `_example` не загружается; чтобы
проверить слой на нём, сделай копию:

```bash
cp -r agents/_example agents/test
sed -i 's/^name: _example$/name: test/' agents/test/agent.md   # name должно совпадать с именем папки
make agent-run AGENT=test PROMPT="Привет! Представься."
```

`agents/test/` в `.gitignore`: копия попадает в образ при сборке, но не в коммит.

### Доступ агента к базе знаний

Инструмент `search_knowledge_base` (`internal/knowledge/kbtool`) ищет по [базе знаний бренда](#база-знаний-бренда).
Агент получает его, только если инструмент перечислен в `tools:` его `agent.md`; правила работы с базой — общий
скилл `brand-knowledge` (`skills/brand-knowledge/SKILL.md`). Оба подключены в шаблоне `agents/_example/`:

```yaml
tools:
  - search_knowledge_base
skills:
  - brand-knowledge
```

Модель передаёт `query` (что найти, своими словами), `limit` (1–20, по умолчанию 5) и `kinds` (фильтр по типу
документа). В ответ приходят фрагменты в тегах `<fragment index="1" source="…" title="…" kind="brand" score="0.83">`:
источник — путь файла в `KB_ROOT`. Защита от промпт-инъекций в материалах: `<` и `&` в тексте фрагмента экранируются,
поэтому фрагмент не может закрыть свой тег или подделать соседний; название и источник — в одну строку, до 200
символов; модели прямо сказано, что фрагменты — данные, а не инструкции. Один вызов ограничен 30 секундами и примерно
16 000 символов фрагментов вместе с названиями и источниками: короткие фрагменты идут целиком, остаток делится между
длинными, обрезка — по границе слова. Неверные аргументы, таймаут и ошибки БД или эмбеддингов не прерывают прогон: модель получает понятный
текст с `is_error` (ошибки инфраструктуры ещё и пишутся в лог), а «ничего не найдено» — обычный результат.

Без `OPENAI_API_KEY` приложение стартует, инструмент остаётся зарегистрированным и отвечает модели, что база
знаний недоступна, а при старте в логе есть предупреждение `agents: tool is unavailable` для каждого агента, у
которого он в `tools:`. Ошибкой старта это не сделано намеренно: ключ OpenAI необязателен, и одна и та же папка
`agents/` должна работать и без него.

Проверка на копии шаблона (нужны `ANTHROPIC_API_KEY` и `OPENAI_API_KEY` в `.env`):

```bash
make up
make kb-ingest KB_PATH=./kb/brand KB_KIND=brand
cp -r agents/_example agents/test
sed -i 's/^name: _example$/name: test/' agents/test/agent.md
make agent-run AGENT=test PROMPT="Напиши короткий пост о том, как мы говорим о питании"
```

Вызовы инструмента и их ошибки видны в логе (`agents: tool failed`, `kbtool: …`).

## База знаний бренда

Материалы бренда (голос, ЦА, продукты, брендбук, лучшие посты) — файлы `.md`, `.txt`, `.docx`, `.pdf` в папке
`./kb` (она в `.gitignore` и `.dockerignore`: материалы тренера не попадают в git и в образ).
Нужны поднятый стек (`make up`) и `OPENAI_API_KEY` в `.env`; Go не нужен: `make kb-*` запускают `/app/kb` из образа
приложения через `docker compose run` (`scripts/kb.sh`), `./kb` монтируется туда только на чтение в `/kb`
(`KB_ROOT=/kb`). `KB_PATH` пишется как на хосте; путь вне `./kb` — ошибка. Права и запуск от root — в
[docs/SETUP.md](docs/SETUP.md), раздел 5. `KB_HOST=1 make kb-…` — запуск через `go run` на хосте (для разработки,
`KB_ROOT` из `.env`). Повторная загрузка неизменённого файла ничего не делает.

```bash
make kb-ingest KB_PATH=./kb/brand KB_KIND=brand     # kind: brand | product | post | other; без KB_PATH — вся ./kb
make kb-search Q="как мы говорим о питании" LIMIT=5
make kb-delete SOURCE=brand/voice.md                 # source — как его напечатал ingest
make kb-reembed                                      # дозаполнить эмбеддинги, перейти на текущую модель
```

`source` документа — путь относительно `KB_ROOT` (`./kb`), поэтому файл получает один и тот же source, загружен ли он один
или вместе с папкой, а одноимённые файлы разных папок не перезаписывают друг друга. Файл вне `KB_ROOT` — ошибка. Файлы
читаются через `os.Root`: симлинк, ведущий наружу (и любой абсолютный симлинк), не читается, а при обходе папки
симлинки пропускаются.
Без `KB_KIND` у существующего документа сохраняется его тип (у нового — `other`); сменить тип можно только
с `KB_FORCE=1` (`-force`): другой тип у того же source обычно значит, что это другой документ.
Документ переиндексируется, если изменились его текст, модель эмбеддингов (`EMBEDDINGS_MODEL`) или версия нарезки.
Поиск идёт только по векторам текущей модели: после смены модели запусти `make kb-reembed`.
Правки тренера, сохранённые без ключа OpenAI, получают векторы тоже через `make kb-reembed`.
Агенты ищут по базе инструментом `search_knowledge_base`: см. [«Доступ агента к базе знаний»](#доступ-агента-к-базе-знаний).

Ограничения: файл до 32 МБ, документ до 1 000 000 символов и 1000 чанков. В PDF читается только текстовый слой
(сканы нужно сначала распознать), колонки и таблицы не восстанавливаются, не больше 1000 страниц.
PDF разбирается в отдельном процессе (`kb extract-pdf`, без переменных окружения, в своей группе процессов): до
30 секунд, память ограничена `GOMEMLIMIT` и на Linux `RLIMIT_AS`, распакованного содержимого — до 1 МБ на страницу
и 16 МБ на документ, у шрифта — до 4096 записей ToUnicode.
Если разборщик падает или зависает, файл пропускается с ошибкой, остальные загружаются.

## Задачи и согласование

Пакет `internal/tasks`: задача от тренера проходит очередь, агент делает черновик, тренер его одобряет, отклоняет
или отправляет на правку. С Telegram-шлюзом задачи связывает `internal/teamchat` (раздел ниже); без токенов ботов
черновики только пишутся в лог (`tasks.LogNotifier`).

```
queued → running → awaiting_approval → approved | rejected
            │                │
            │                ├→ queued   (правка: следующий запуск даёт версию +1)
            │                └→ failed   (черновик не удалось отправить за TASKS_DELIVERY_ATTEMPTS попыток)
            ├→ queued   (временная ошибка: повтор с экспоненциальной задержкой)
            ├→ failed   (первый черновик не получился: попытки кончились или ошибка постоянная)
            └→ awaiting_approval прошлой версии (правка не получилась: черновик приходит снова с пояснением)
```

- **Создание** — `Service.Create(CreateTaskData)`: агент, тип задачи, текст, ссылки на медиа и исходное сообщение.
  Ключ идемпотентности — `(chat_id, message_id)` (id сообщения уникален в чате, топик в ключ не входит): повторная
  доставка того же сообщения возвращает существующую задачу (уникальный индекс + `ON CONFLICT DO NOTHING`).
- **Очередь** — Redis Stream `TASKS_STREAM` с consumer group: сообщение остаётся в pending до ack, а сообщение упавшего
  воркера забирает другой (`XAUTOCLAIM` через `TASKS_TIMEOUT` + 1 мин). Повторы ждут в sorted set `<stream>:delayed` и
  переносятся в stream Lua-скриптом, когда подходит время. Источник правды о статусе — Postgres: каждое изменение
  идёт в транзакции с `SELECT ... FOR UPDATE` функцией-апдейтером (`UpdateToXxx`). Каждый запуск получает случайный
  `run_id`: записать результат может только он, поэтому дубль сообщения или перехваченный запуск ничего не ломают.
- **Sweeper** (сразу при старте и каждые `TASKS_SWEEP_INTERVAL`) ставит в очередь то, что очередь потеряла: задачи,
  поставленные в очередь давно (`enqueued_at` старше таймаута + 1 мин) и не взятые, и `running`, чей воркер умер.
  Найденную задачу он помечает поставленной, поэтому не дублирует её в очереди на каждом проходе. Зависший `running`
  перезапускается только в пределах `TASKS_MAX_ATTEMPTS`.
- **Запуск** — воркер переводит задачу в `running`, запускает агента (`tasks.Executor`, по умолчанию
  `agents.Runtime`; паника агента — ошибка запуска, процесс не падает), сохраняет новую версию и отправляет черновик
  с кнопками. Результат, полученный до остановки, сохраняется и отправляется даже во время остановки.
- **Доставка черновика** — отправляет только тот, кто атомарно захватил её (воркер или sweeper) на время аренды
  (2 мин; одна отправка ограничена 30 с). Неудачная отправка повторяется с задержкой, после `TASKS_DELIVERY_ATTEMPTS`
  попыток задача `failed`. Гарантия — «хотя бы один раз», а не «ровно один»: дубль возможен, если сообщение ушло, а
  его id не удалось записать (запись повторяется 3 раза) или отправка оборвалась по таймауту уже после того, как
  Telegram её принял. Если два отправителя всё же отправили черновик, остаётся сообщение, записанное первым, а у
  лишнего убираются кнопки (`CloseDraft` с `Duplicate`).
- **Ответ на старое сообщение черновика** (на прошлую версию, на заменённое или лишнее сообщение) — `ErrStaleDraft`,
  тренеру: «Ответьте на последний черновик».
- **Кнопки** — `callback_data` вида `t:<task_id>:<version>:<a|r|x>` (одобрить / правки / отклонить), не длиннее 64 байт:
  `tasks.EncodeCallback` / `tasks.ParseCallback`, набор кнопок — `tasks.DraftButtons`. Действия: `Approve`, `Reject`,
  `RequestRevision`, а правка ответом на черновик — `RequestRevisionByReply` (задача ищется по id сообщения черновика).
  Действие по устаревшей версии — `ErrStaleVersion`, повторное нажатие — `ErrConflict`; текст для ответа тренеру
  даёт `tasks.UserMessage(err)`. Кнопка «Правки» сама правку не создаёт: шлюз просит ответить на черновик текстом.
- **Правка** сохраняется в `task_feedback`, и в той же транзакции задача снова ставится в очередь. Агент получает
  прошлую версию и текст правки в тегах `<previous_version>` и `<trainer_revision>` с пометкой, что это данные, а не
  инструкции. Если правку применить не удалось, прошлая версия приходит снова с кнопками и пояснением: её можно
  одобрить или дать правку ещё раз.
- **База знаний** — при одобрении версии, сделанной по правке, пара «прошлая версия → одобренная» с текстом правки
  сохраняется как правка тренера (`kb_corrections`) в фоне: ответ на кнопку не ждёт эмбеддинги; при остановке
  приложение дожидается этих записей. Неодобренные версии туда не попадают.
- **Сообщения тренеру** об ошибках — только понятная причина по классу ошибки (отказ модели, таймаут, недоступность
  сервиса); текст внутренней ошибки остаётся в логе и в `tasks.last_error`.
- **`/status`** — `Service.StatusReport(since)`: число задач в каждом статусе и расход LLM за период из `llm_usage`.
- **Остановка** — воркеры перестают брать задачи сразу, выполняющиеся дорабатывают `TASKS_SHUTDOWN_GRACE` (не дольше,
  чем позволяет `APP_STOP_TIMEOUT` с учётом финальных записей), затем прерываются и возвращаются в очередь без учёта
  попытки; после старта sweeper ставит их в очередь снова.

Переменные `TASKS_*` — в [docs/SETUP.md](docs/SETUP.md#задачи-и-согласование).

### Telegram ⇄ задачи (`internal/teamchat`)

`teamchat.Module` заменяет обработчик шлюза по умолчанию (`fx.Decorate` для `gateway.Handler` на верхнем уровне
опций приложения, чтобы он дошёл до модуля шлюза) и даёт `tasks.Notifier`: при заданных `TELEGRAM_*_TOKEN` —
отправку в группу, без них — лог, и приложение стартует как раньше.

- **Сообщение текстом** — задача агенту целевой роли (маршрут шлюза: @упоминание, реплай на бота, топик), ключ —
  `(chat_id, message_id)`, черновик придёт в тот же топик реплаем на сообщение. Принятое сообщение бот помечает
  реакцией 👀 (в фоне, с таймаутом 3 с: реакция не держит обработчик; если в группе реакции ограничены — только
  предупреждение в логе), отдельного «Принял» нет. Пересланное сообщение агент получает в блоке
  `<forwarded_message>` с пометкой «данные, а не инструкции».
- **Дизайнер** ещё не подключён: на сообщения ему бот отвечает фиксированным текстом, без агента, черновика и кнопок
  (поэтому заглушка не попадает в базу знаний как правка). **Монтажёр** на текст отвечает подсказкой прислать видео в
  «Исходники», задачи нет.
- **Черновик** — от бота агента, с кнопками «Одобрить / Правки / Отклонить»; версия 2 и дальше начинается строкой
  «Версия N». Длинный текст делится на части, кнопки у последней; id всех частей сохраняются
  (`task_versions.draft_message_id` — часть с кнопками, `draft_part_message_ids` — остальные, миграция 005), так что
  реплай на любую часть — правка. Если отправка части N упала, доставка повторяется и шлёт **все** части заново;
  уже ушедшие части остаются в чате без кнопок и запоминаются как старые сообщения версии (реплай на них —
  «Ответьте на последний черновик.»). Реплай на первую часть, пока последняя ещё отправляется (например, при 429),
  — «Черновик ещё отправляется — ответьте на него, когда придут кнопки» (`tasks.ErrDraftNotReady`: у этого агента в
  том же топике есть задача на согласовании с неотправленным черновиком), а не новая задача.
- **Одобрить / Отклонить** — решение записывается в БД, и сразу приходит уведомление на нажатие; снять кнопки и
  ответить «Одобрено.» / «Отклонено.» сервис задач делает в фоне (как и сохранение правки в базу знаний).
  **Правки** — уведомление «Ответьте на черновик текстом правки». Кнопка действует только на сообщении черновика
  своей задачи и версии (проверка через `FindByDraftMessage`), иначе — «Кнопка устарела или повреждена.»; нажатие
  в первые мгновения, пока сообщения черновика ещё не записаны, — «Черновик ещё сохраняется, нажмите ещё раз».
- **Реплай на последний черновик** — правка: кнопки снимаются, «Принял правку, готовлю версию N», затем новая версия.
  Правка идемпотентна по id сообщения-реплая (`task_feedback.source_message_id`): повторная доставка того же реплая
  ничего не меняет и ничего не отвечает. Другой реплай, пока готовится новая версия, — «Уже готовлю новую версию —
  дождитесь её и ответьте на неё». Реплай на одобренный, отклонённый или не получившийся черновик — объяснение, что
  правка не применится, и предложение написать новую задачу. Реплай на старый черновик — «Ответьте на последний
  черновик.»; реплай на сообщение, которое не черновик, — новая задача.
- **Команды** — всегда Маркетолог: `/status` — задачи по статусам и расход LLM за 7 дней; `/plan [пожелания]` и
  `/idea <текст>` — задачи Маркетологу с типом `plan` / `idea`; `/pause` — честное «пока не поддерживается».
- **Бэклог идей** (`internal/ideas`, T2.4). На `/idea <текст>` Маркетолог отвечает карточкой: заголовок, о чём ролик
  (1–3 предложения), формат (разговорный рилс, рилс-тренировка, карусель или другое) и хук. Модель отвечает
  инструментом `submit_idea`, карточка хранится полями (`idea_cards`), текст черновика собирает код. Кнопка
  «Одобрить» у карточки называется «В бэклог»: одобренная карточка становится идеей с номером, Маркетолог отвечает
  «Идея №N в бэклоге…»; «Правки» реплаем — новая версия карточки, «Отклонить» — идея не сохраняется. Одна идея на
  задачу: повторное нажатие или доставка дубля не создаёт. `/ideas` — новые идеи (сверху свежие, 15 строк и
  «…и ещё N», даты — в `TEAM_TIMEZONE`), `/idea_done N` и `/idea_drop N` — сделана / не нужна; отвечают сразу, без
  задачи и модели; пересланные `/idea_done` и `/idea_drop` не выполняются. Идеи из обычных сообщений без `/idea` не
  распознаются.
  Любая другая команда — не задача: в ответ «Такой команды нет. Команды — /help.» (раньше заглушек Монтажёра и
  Дизайнера). Командой считается только сообщение с сущностью `bot_command` в начале (`Event.IsCommand`), поэтому
  правка «/2 подхода убрать» остаётся правкой.
- **Онбординг** (T4.3a). `/help` и `/start` — что умеет каждая роль, куда что слать, команды, примеры правок
  Монтажёру и как оставить отзыв; в топике сначала блок про этот топик. Меню команд (ввод «/») задаёт шлюз при старте
  через `setMyCommands` только у бота Маркетолога, в области группы (`/help`, `/idea`, `/ideas`, `/idea_done`,
  `/idea_drop`, `/feedback`, `/status`; `/plan` и `/pause` работают, но в меню не показаны); у остальных трёх ботов
  меню удаляется (группа, все группы, по умолчанию), чтобы команды не дублировались. `/onboard` (только
  `TELEGRAM_ADMIN_USER_IDS`, пусто — любой из белого списка) публикует приветствия в «Планёрке» от Маркетолога, в
  «Исходниках» и «Продакшне» — от Монтажёра, и закрепляет их ботом Маркетолога; id, топик и признак закрепа хранятся
  в Postgres (`onboarding_messages`), повторный вызов редактирует их без нового закрепа, а удалённое приветствие или
  приветствие сменившегося топика заменяет новым (старое открепляется). Нет права на закреп — честный ответ и сообщение в «Техничку». Подсказки вместо тупиков (неизвестная
  команда, текст Монтажёру, Дизайнер, голосовые, фото, аудио) ссылаются на `/help`.
- **Отзывы и метрики пилота** (T4.5, `internal/pilot`, миграция 008). `/feedback <текст>` в любом топике сохраняется
  в `feedback` (автор, текст до 2000 символов с пометкой об обрезке, топик, задача и версия — если это реплай на
  черновик), копия уходит в «Техничку» от Маркетолога со ссылкой на сообщение, тренеру — «Спасибо, передал команде.»;
  пустой — подсказка, пересланный — не принимается, повторная доставка не дублирует запись и копию, но благодарит
  снова. Метрики считаются по `tasks`, `task_versions` и `task_feedback` за период (задачи, созданные в нём): по
  агентам (карточки `/idea` — отдельной строкой «Идеи») — создано, одобрено, из них без правок (доля), правок до
  одобрения в среднем (по запросам правок: неудачная правка версию не меняет), отклонено, сбоев; у Монтажёра — время
  от задачи до первого черновика (медиана и максимум); плюс число отзывов. `/status` дописывает блок за 7 дней. Еженедельная сводка в «Техничку» — в
  `PILOT_REPORT_WEEKDAY` и `PILOT_REPORT_TIME` (`TEAM_TIMEZONE`; пусто — выключено) одним сообщением с отзывами недели
  (что не влезло — «…и ещё N»); неделя
  отмечается в `pilot_reports` до отправки, поэтому рестарт не шлёт её дважды; пропущенная (app был выключен) сводка
  досылается в течение суток.
- **Видео для Монтажёра** (топик «Исходники» или упоминание его бота; видео или видео-файл) шлюз скачивает, а
  `teamchat` сразу, в том же слоте события, копирует его в S3 (`internal/media`, ключ
  `<MEDIA_KEY_PREFIX>/<chat id>/<message id>/<file_unique_id>.<ext>`; расширение — по MIME, имя файла от
  пользователя в ключ не попадает) и создаёт задачу Монтажёра (`reels-edit`, подпись — её вход); от Монтажёра —
  «Исходник получил, начинаю монтаж. Пришлю черновик в «Продакшн»…». Повторная доставка пишет тот же ключ и находит
  ту же задачу, второй ответ отсекает метка события в Redis.
- **Монтажёр** (T3.4b): задачу выполняет сервис `media-worker` (`internal/editjob` — задания и результаты в Redis,
  `internal/mediaworker` — конвейер, `internal/editor` — сторона app). Конвейер: исходник из S3 → проверка (картинка,
  звук, не длиннее `MEDIA_WORKER_MAX_SOURCE_DURATION`) → Whisper → план склейки (паузы, паразиты, оборванные дубли;
  спорные повторы остаются) → склейка, фирменные субтитры и экспорт под Instagram одним проходом ffmpeg
  (1080×1920, H.264 High, yuv420p, AAC 48 кГц, fps исходника, но не выше 30, `+faststart`; не 9:16 — с полями,
  `MEDIA_WORKER_FIT=crop` — с обрезкой) → рилс, `plan.json`, `decisions.log` и транскрипт исходника в S3 под
  `MEDIA_RESULT_PREFIX`. Черновик — видео от бота Монтажёра в «Продакшн» со ссылкой на исходник, описанием
  (было/стало, сколько вырезано, подпись тренера) и кнопками. Пока идёт монтаж, задача «в очереди» и не занимает
  воркер задач. Задание задачи, которую app уже провалил (воркер не был запущен, таймаут), воркер пропускает без
  скачивания и Whisper, даже если его запись осталась в очереди.
- **Правки Монтажёру** (T3.4c): реплай на видео-черновик («убери первые 3 секунды», «оставь второй дубль», «верни
  фразу про дыхание», «в субтитрах Прокудина, а не Прокудино») — новая версия видео. Модель решает по транскрипту и
  плану прошлой версии, app проверяет её план, воркер монтирует из сохранённого транскрипта (Whisper повторно не
  вызывается) под ключами новой версии, прошлые версии остаются. Подпись к исходнику применяется как правка к первому
  монтажу, спорные повторы решает модель с объяснением в `decisions.log`. Музыка, B-roll, цвет, скорость,
  перестановка и стиль субтитров — честный отказ «Такое я пока не умею…»; непонятная правка — «Не понял, что именно
  поменять…».
- **Тренировки** (T3.10): у монтажа есть режим — `talk` (разговорный, как раньше) или `workout` (ролик целиком, паузы
  и молчаливые отрезки — это упражнения, режется только указанное). Режим выбирает модель по подписи и речи, тренер может
  попросить сама («тренировка», «не режь паузы»). Ролик, где речи мало (разговорная склейка оставила бы меньше
  `MEDIA_WORKER_MIN_SPEECH_SHARE` исходника) или нет вовсе, не режется вслепую: воркер останавливается с планом
  «тренировка» и модель решает даже без подписи; если модель недоступна, черновик — весь ролик с пометкой. Подписи
  упражнений («Выпады — 12 раз») модель ставит по слову, где тренер называет упражнение, или по секундам из подписи;
  время не выдумывает — что не поставлено, названо в описании с подсказкой «подпиши выпады с 0:15 до 0:45». Стиль
  подписей — раздел `title` в `assets/subtitles/style.yaml`. «Убери звук» убирает звук исходника и субтитры речи (трек
  тренер ставит в Instagram); фразы, которые распознавание выдумало на музыке, Монтажёр скрывает только в субтитрах
  (`hide_words`), не вырезая кадры упражнения. Черновик длиннее `EDITOR_REELS_MAX_DURATION` (3 мин) приходит с пометкой.
  Порог `MEDIA_WORKER_MIN_SPEECH_SHARE` — 0,35 (T3.19a; замер: «говорящая голова» тренера 0,44–0,58, тренировка 0,26,
  музыка 0,01): прежние 0,6 отправляли в тренировку обычный разговорный ролик.
- **Чистка первой версии** (T3.19a, `EDITOR_CLEANUP=true`): первую версию разговорного ролика — с подписью и без —
  модель чистит от брака съёмки: неудачные дубли (та же мысль ещё раз через 5–90 с: остаётся последний полный
  вариант), повторы подряд («ну привет» ×3 → одно) и подготовку к съёмке (отсчёт «раз, два, три», «начинаем», «это
  последний дубль», обращения к оператору, реплики при выходе из кадра). Это не сокращение: содержательное не
  трогается. Без подписи модель не задаёт длину, не режет по времени, не ставит подписи упражнений и не убирает звук
  (тренировку с комментариями может отметить режимом workout, но тогда ничего не вырезает); чистка, оставившая меньше
  четверти ролика или меньше 15 с, возвращается модели с причиной, а после второй неудачи черновик — автоматическая
  склейка с пометкой. В промпте — подсказки программы: похожие фразы (грубое сравнение основ слов без стоп-слов;
  пункты списка с разными числительными и ряд из трёх похожих, но разных фраз не считаются; одна и та же фраза подряд — повтор), повторы подряд внутри фразы и
  фразы со словами про съёмку. В описании черновика — одна строка «Убрал неудачные дубли и подготовку к съёмке: 3
  фрагмента (52,4 с).», а «неудачные дубли» в заголовке — только если они действительно вырезаны; в `decisions.log` —
  каждый вырезанный отрезок. Модель недоступна — черновик с автоматической склейкой. Правила — раздел «Чистка дублей и
  подготовки» в `agents/editor/agent.md`.
- **Невыполнимые просьбы** (T3.19a): музыку, цвет, эффекты и переходы, вставки, ускорение, фильтры красоты и
  перестановку фрагментов модель отмечает категорией (`declined` в `submit_edit`), а тренер получает заготовленный
  текст («Музыку добавьте в Instagram при публикации — я её не накладываю.»): в подписи — вместе с выполненной частью
  или вместо неё, в правке — вместе с выполненной частью или как отказ. Свободный текст модели тренеру не показывается.
- **Длина** — по умолчанию ролик не сокращается (`EDITOR_REELS_TARGET_DURATION=0`: разговорные рилс тренера идут по
  2–3 мин); сократить можно подписью или правкой с длиной («сделай 40 секунд»).
- **Редакторский монтаж** (T3.16a): разговорный ролик, который после чистки длиннее `EDITOR_REELS_TARGET_DURATION`
  (60 с) больше чем на 10 % (длиннее 66 с), отдаётся модели даже без подписи и спорных повторов: она оставляет лучшее — хук в первых секундах, одну мысль
  законченными фразами, финальную мысль или призыв — так, чтобы рилс был 30–60 с, и вырезает остальное целыми фразами
  (перестановки и ускорения нет). Длину можно назвать в подписи или правке («сделай 40 секунд», «до 30 секунд»,
  «начни с фразы про колени», «не сокращай»): app проверяет, что рилс уложился в ±15 %, иначе модель исправляет решение. В описании
  черновика — «сократил под рилс», начало и финал, что не вошло; в `decisions.log` — причина отбора, длина и каждая
  невошедшая фраза. До 66 с — модель не вызывается; модель недоступна — только чистка с пометкой «Ролик длиннее
  рекомендованных…». Расшифровка в промпте — по фразам до 8 слов с диапазонами индексов слов (больше чем втрое
  короче, чем по слову на строку). Правила отбора — раздел «Редакторский отбор» в `agents/editor/agent.md`, стиль тренера дополняется
  в разделе «Стиль тренера».
- **Заголовок-хук** (T3.15b): текст сверху кадра на первые секунды рилс («видео для тех, кто боится начать
  тренироваться дома», «мой ребёнок билингв»). Текст предлагает модель для каждой первой версии — обращение к аудитории
  или личный факт/тезис из речи, до 14 слов и 90 символов, без обещаний, которых нет в ролике, — поэтому при
  `EDITOR_HOOK_TITLE=true` каждая первая версия ждёт одного вызова модели; модель недоступна — черновик без заголовка.
  Рисует его libass стилем `hook` из `assets/subtitles/style.yaml`: Manrope Regular 60 px, белый с мягкой тенью, по
  центру, до 4 строк с переносом по словам (жёлтое ключевое слово и плашка под строками — опции, по умолчанию
  выключены). Показывается до конца первой фразы + 0,5 с, но от 2,5 до 8 с и не дольше ролика; на это время субтитры
  стоят сразу под ним, а затемнение продлевается под них. Заголовок модели — со строчной буквы, как в референсах: если
  в первом слове нет других заглавных (аббревиатура, «YouTube»), app делает первую букву строчной; текст, который тренер
  продиктовала в подписи или правке, и пункты на экране остаются как есть. Ролику без подписи модель
  предлагает заголовок вместе с чисткой; если заголовка не нашлось, в описании — подсказка, как добавить его правкой. Правкой
  «поменяй заголовок на …», «добавь заголовок …», «убери заголовок» — новая версия без Whisper; в описании черновика —
  «Заголовок: «…».» или «Убрал заголовок.». Правила текста — раздел «Заголовок-хук» в `agents/editor/agent.md`.
- **Пункты и цифры на экране** (T3.17, только разговорный ролик): когда тренер перечисляет («во-первых…», «три
  причины») или называет цифры и сроки, модель выносит их на экран (`screen_notes` в `submit_edit`, до 12 элементов,
  до 40 символов, только из сказанного): заголовок списка («3 вещи»), пункты («1/ на русском»), которые копятся строками
  под ним и держатся до конца списка, и короткие выноски («6 лет») на 1,5–3 с. Рисуются стилем хука на его месте,
  после того как хук ушёл (элемент ждёт его конца); влезает 4 строки — ранние пункты уезжают вверх. Элемент на
  вырезанном куске не показывается. Ролику без подписи модель может предложить пункты вместе с хуком и чисткой. Правкой «убери пункты», «поменяй пункт 2 на …», «добавь выноску … на …» — новая версия без
  Whisper; в описании черновика — «На экране: 3 пункта и 2 выноски.» или «Убрал пункты и цифры с экрана.».
- **Ник и карточка** (T3.17): `REELS_HANDLE` (например `@prokudina.ana`, строго `@` и `a-z0-9._`; пусто — ничего)
  рисуется мелко белым с тенью у правого края на уровне слов весь ролик, с простым векторным значком Instagram
  (`REELS_HANDLE_ICON`); в последние 2 с (`REELS_END_CARD`; не больше трети ролика, до неё ≥ 2 с) кадр плавно темнеет
  и по центру крупно значок и ник, слова и пункты заканчиваются там, где она начинается, — ролик не удлиняется, звук не
  трогается. И в разговорном ролике, и в тренировке. Ник проверяют и app (при старте), и
  воркер (в задании).
- **Голосовые и видеокружки** принципиально не обрабатываются: тренер диктует текст диктовкой телефона. **Фото,
  аудиофайлы, видео не Монтажёру** — честный ответ. Всё это шлюз даже не скачивает: `teamchat.Handler` реализует
  `gateway.MediaFilter` (`WantsMedia` true только для видео Монтажёру).
- **Ошибки** — тренеру `tasks.UserMessage` (класс ошибки) в тот же топик, подробности — только в лог.
- **Остановка** — хуки ожидания фоновой работы (`tasks.Service` и `teamchat.Handler`) регистрируются в их
  конструкторах, а шлюз и воркеры создаются позже, поэтому fx останавливает их раньше: пока ждём фоновую работу,
  новых событий и нажатий нет (`TestIntegrationStopOrder`).

Ручная проверка M1 по шагам — [docs/SETUP.md](docs/SETUP.md#ручная-проверка-m1).

## Проверка Монтажёра без Telegram (`make edit`)

Владельцу — проверить весь путь монтажа на своём видео без группы: тот же app-путь (модель Монтажёра, её решения и
правки, `editor.Executor`) и тот же `media-worker`, но без шлюза Telegram и без очереди задач — в группу ничего не
уходит, задач в Postgres нет. Нужен запущенный стек (`make up`) и `ANTHROPIC_API_KEY`, `OPENAI_API_KEY` в `.env`;
новых переменных нет. Если образ приложения или media-worker старше кода, команда просит `make up` (он пересоберёт
оба).

```bash
make edit FILE="$HOME/Movies/clip.mov"                          # версия 1 в ./edits/clip/v1
make edit FILE="$HOME/Movies/clip.mov" CAPTION="оставь второй дубль" OUT=./edits/clip-2
make edit OUT=./edits/clip REVISION="сделай 40 секунд"           # правка последней версии → ./edits/clip/v2
make edit OUT=./edits/clip                                       # докачать версию, если скачивание прервалось
```

`~/…` в `FILE` и `OUT` тоже понимается (zsh на macOS не раскрывает его в `make FILE=~/…`, это делает скрипт), но
надёжнее `"$HOME/…"`. `$` и кавычки в `CAPTION`/`REVISION` передаются как есть — экранировать `$` не нужно.

- В `OUT/v<N>/`: `reel.mp4`, `plan.json`, `decisions.log`, `description.txt` (текст черновика, как его увидел бы
  тренер), `timings.txt` (загрузка в S3, очередь/транскрипция/план воркера, модель, рендер, скачивание, итого; время
  ожидания относится к стадии задания на доске после каждого прогона). В stdout — сводка: версия, задача, время по
  стадиям, число вызовов модели и их стоимость за этот запуск. Логи — JSON в stderr.
- Решения — те же, что у бота, по тем же настройкам из `.env`: с `EDITOR_HOOK_TITLE=true` (по умолчанию) первая
  версия всегда идёт через модель ради заголовка-хука; редакторский отбор длинной «говорящей головы» — только если
  задан `EDITOR_REELS_TARGET_DURATION` (по умолчанию 0 — выключен).
- **Ctrl+C останавливает монтаж**: задание снимается с доски, и воркер отменяет его за несколько секунд (проверка доски
  раз в 3 с — и во время транскрипции); версия не записывается.
- **Убитый запуск** (`docker kill`, закрытый терминал): задание держится арендой — ключом в Redis, который запуск
  продлевает каждые 5 с с TTL 20 с. Без продления воркер отменяет задание до 25 с после убийства, а не рендерит для
  никого. Следующий `make edit` той же версии снимает с доски задание убитого запуска (кроме уже готового для той же
  подписи или правки) и монтирует заново. Если запуск жив, но аренда истекла (Mac уснул, Docker на паузе), воркер
  отдаёт временный сбой, и запуск сразу повторяет задание. Если аренду той же версии держит другой запуск, `make edit`
  останавливается: «эту версию монтирует другой запуск make edit: дождитесь его». Расход модели убитого запуска в сводку не попадает (её некому напечатать) — он есть только в
  `llm_usage`.
- **macOS, терминал IDE**: у терминала VS Code/GoLand может не быть доступа к `~/Desktop`, `~/Documents` и
  `~/Downloads` (защита TCC) — тогда `make edit` пишет, что файла нет или он не читается. Положите исходник в папку
  проекта, например `./edits/src/` (она в `.gitignore`), или дайте IDE доступ: «Системные настройки → Конфиденциальность
  и безопасность → Файлы и папки» (или «Полный доступ к диску»).
- `OUT/state.json` (`"format": 1`) — задача, ключ исходника в S3, подпись, последняя версия и тексты правок: по нему
  `REVISION` делает версию N+1 так же, как реплай на черновик. Версия, сделанная воркером, сначала записывается как
  недокачанная (`pending`); если скачивание прервалось, `make edit OUT=…` без `FILE` и `REVISION` только докачивает её.
  Если Монтажёр правку не применил, печатается текст, который получил бы тренер, версия не растёт, команда завершается
  ошибкой (`edit-local` — код 1, `make` — свой код 2). В `OUT`, где уже есть монтаж, новый `FILE` не принимается
  (если там недокачанная версия — подсказка, как её докачать).
- В одной `OUT` одновременно работает один запуск: `OUT/.lock` (PID, хост — ID контейнера, время). Если контейнера
  прошлого запуска больше нет (убит), `make edit` сам снимает блокировку: «предыдущий запуск прерван, снимаю
  блокировку»; если он работает — говорит, какой контейнер ждать или остановить. Запуск удаляет только свой lock.
- Задача синтетическая: ID = 10^18 + счётчик Redis `edit-local:seq` (у задач app — bigserial, до этого диапазона не
  дойдёт), исходник — в S3 как видео чата `1` под случайным именем `local-<8 hex>`. Ключ, уже занятый в S3 (например,
  после сброса Redis счётчик начался заново), не перезаписывается — берётся следующий ID. Если исходника в S3 больше
  нет (проверка — HEAD-запросом), правка не начинается: «исходник не найден в S3 — начните заново». Waker работающего app такую задачу не находит
  и пропускает.
- **S3 не чистится**: исходники (`incoming/1/…`) и результаты (`edits/1/…`) локальных прогонов остаются в бакете, пока
  их не удалить вручную.
- **Локальные задания идут в ту же очередь воркера, что и задания тренера** (один `media-worker`, по одному заданию за
  раз): на VPS во время пилота `make edit` не запускать — тренер будет ждать свой черновик.
- Расход: сводка считает вызовы по результатам `agents.Runtime`, включая частичный результат (max_tokens, отказ,
  лимит шагов); вызовы прогона, упавшего на ошибке API без результата, в сводку не попадают. Точная сумма — в
  `llm_usage` (каждый вызов пишется, как в app), но там локальные прогоны не отличить от боевых: агент тот же, `editor`.
- Безопасность: видео монтируется в контейнер только для чтения (один файл), проверяется как у бота — тип видео
  (mp4, mov, webm, mkv, avi, 3gp, mpeg), не пустое, не больше `TELEGRAM_MAX_FILE_SIZE`; длительность ограничивает воркер
  (`MEDIA_WORKER_MAX_SOURCE_DURATION`). `OUT` по умолчанию — `./edits/<имя файла>` (в `.gitignore`); путь берётся
  реальный (символические ссылки раскрываются): внутри проекта — только подпапки `./edits/`, вне проекта — любая
  отдельная папка, кроме `/` и папок, в которых лежат проект или домашняя папка (на macOS — без учёта регистра).
  Контейнер работает с uid:gid
  пользователя, файлы в `OUT` — его. «Техничка» никуда не шлётся: отчёт — в лог.
- Без `make up` или без `media-worker` команда сразу говорит, что поднять (ничего не загружает). Временные сбои
  повторяются как в очереди задач (`TASKS_MAX_ATTEMPTS`, `TASKS_RETRY_*`), каждый прогон ограничен `TASKS_TIMEOUT`,
  ожидание воркера — опросом раз в 5 с и по каналу `done`; старт и остановка — `APP_START_TIMEOUT`/`APP_STOP_TIMEOUT`.
- Проверка в CI: `mediaworker.TestIntegrationEditLocalRevision` (Redis, S3 и конвейер с ffmpeg: v1 → правка → v2 без
  Whisper), `TestIntegrationEditLocalCaption` (подпись: planned → модель → render), `TestIntegrationEditLocalHook` (хук через
  модель за `UsageMeter`, правка «убери заголовок») и шаг compose-smoke «Editor without
  Telegram» (бинарь, проверки аргументов и OUT, прогон без ключей до отказа воркера).

## Разработка

Правила — в [AGENTS.md](AGENTS.md) и [CODE_STYLE.md](CODE_STYLE.md). Проверки: `make check` (lint + `go test -race`).

CI (`.github/workflows/ci.yml`): job `tidy` делает `go mod tidy` и на ветках `feature/**`, `fix/**`, `refactoring/**`
сам коммитит `go.mod`/`go.sum` (после этого сделай `git pull`), затем `check` и `compose-smoke` проверяют итоговый коммит.
`check` требует, чтобы ветка содержала актуальный `main`: перед мержем сделай rebase. Новые миграции ветки
должны иметь номер больше последней миграции в `main` (golang-migrate молча пропускает меньший номер), а уже
смерженные миграции нельзя править, удалять и переименовывать.

### Интеграционные тесты

Тесты с `Integration` в имени работают с PostgreSQL из compose и подключаются через `pgtest.Connect`: он создаёт
для каждого теста отдельную базу `pgtest_*`, накатывает в неё все миграции и удаляет её в конце теста.
Без `INTEGRATION=1` они пропускаются, поэтому `make test` базы не требует. `make test-integration` печатает
подробный вывод (`-v`) и падает, если какой-то тест пропущен (`--- SKIP`) или не прошёл ни один: интеграционный тест
при `INTEGRATION=1` не должен вызывать `t.Skip`.

```bash
make up && make test-integration
```

Тесты очереди работают с Redis: Redis из compose наружу не опубликован, поэтому `make test-integration` сам
поднимает отдельный одноразовый контейнер Redis (`ai-agents-redis-test`, без тома, на `127.0.0.1:6380`, порт —
`REDIS_TEST_HOST_PORT`), передаёт тестам его адрес в `REDIS_TEST_ADDRESS` и удаляет контейнер по окончании
(вручную — `make redis-test-down`).
Ключи каждого теста — со своим префиксом (`internal/redistest`).
Так же для S3: `make test-integration` поднимает одноразовый RustFS (`ai-agents-s3-test`, образ сервиса `s3` из
`docker-compose.yml`, анонимный том, тестовые ключи, `127.0.0.1:9100`, порт — `S3_TEST_HOST_PORT`), передаёт тестам
`S3_TEST_ENDPOINT`, `S3_TEST_ACCESS_KEY`, `S3_TEST_SECRET_KEY` и удаляет контейнер с томом по окончании (вручную —
`make s3-test-down`). Каждый тест получает свой бакет, который удаляется после теста (`internal/s3test`).

`TestIntegrationPipeline` (конвейер Монтажёра) рендерит настоящим ffmpeg с libass, поэтому `make test-integration`
требует ffmpeg на хосте (macOS: `brew install ffmpeg`); в CI он идёт ещё и внутри образа `media` (job `media-image`).
В CI они идут в job `compose-smoke`. Тесты не видят данных друг друга и данных `POSTGRES_DB`, поэтому могут
вызывать `t.Parallel`. Пользователю БД нужно право `CREATEDB` (у пользователя из compose оно есть). Базы `pgtest_*`,
оставшиеся после убитого прогона, можно удалить вручную.
